### T1 轮询丢事件 vs 中断
**题目**：为什么轮询可能「丢事件」，而中断不会？
**标准/记忆点**：
- 轮询是**采样**——只在查询瞬间看一眼；按下→松开发生在两次查询之间 → 根本没被采样到（电平已变回）
- 中断 = 硬件在边沿变化瞬间触发（边沿触发 vs 电平采样），监视不花 CPU
- 记忆点：**轮询丢事件 = 没采样到**（不是来不及处理）
**作答史**：
- 2026-08-06 ✅ 知道和 CPU 忙有关，纠正后补「没采样到」本质（批次 1 Q1）

### T2 置标志 + 主循环消费（事件降维）
**题目**：为什么「ISR 置标志 + 主循环消费」能同时满足 ISR 短 + 响应及时？
**标准/记忆点**：
- 原子性：ESP32 bool/unsigned long 32 位对齐读写硬件原子（不撕裂才敢跨上下文共享）
- 及时性本质 = 消费**内存标志**（纳秒级）不是轮询硬件引脚——把「硬件事件」降维成「内存状态」
- 深一层：标志 1 bit 快速连按合并丢失 → 计数器/FreeRTOS 队列
- 记忆点：**事件降维 = 硬件读变内存读**
**作答史**：
- 2026-08-06 ✅ 原子性 + 消费解耦都答到（批次 1 Q2）
**状态**：✅（队列解法 → T5）

### T3 volatile 判据
**题目**：为什么 btnPressed 必须 volatile，DEBOUNCE_MS 不需要？
**标准/记忆点**：
- 判据：是否被**当前执行流之外**修改——ISR 是另一条执行流（硬件触发），主循环管不着它何时写 → 必须每次重读内存
- DEBOUNCE_MS = const + 编译期可知 → **常量折叠**直接内联进指令，连内存都不读
- 记忆点：**volatile 判据 = 执行流之外修改**
**作答史**：
- 2026-08-06 ✅ 判据方向对（会不会被中断修改），精确化为「执行流之外」（批次 1 Q3）
**状态**：✅

### T4 防抖两层（delay vs 时间戳）
**题目**：为什么防抖用「时间戳过滤」而不是「delay(10)」？
**标准/记忆点**：
- delay 三宗罪：**忙等阻塞**（CPU 停摆 + ISR 里 delay = 主循环挂起 + 看门狗复位）+ **时长拍脑袋**（短了防不住 5-20ms 弹跳、长了吞掉合法连按）+ **吞真事件**（delay 等待窗口内按键再次变化会被吞掉/误判）
- 时间戳 = **非阻塞仲裁**：记录上次有效边沿时间戳，间隔 < 阈值判为抖动忽略，≥ 阈值接受为新事件；期间主循环照常跑、事件不丢
- 中断每次下降沿硬件无条件触发——时间戳不是触发开关，是 ISR 内仲裁：**触发 ≠ 有效，硬件触发 vs 软件过滤**
- 类比：硬件触发 = webhook 每次都推；时间戳过滤 = 消费端去重/冷却
- 记忆点：**防抖 = 时间过滤，不是等一等再读**（丢的是噪声不是事件）
**作答史**：
- 2026-08-06 ✅ 阻塞+拍脑袋+丢事件全答到（批次 1 Q4）
- 2026-08-14 ⚠️ 复检半对：漏最致命的「吞真事件」，补正后确认（W1-3 复检）
- 2026-08-19 ✅ 直考通过：delay=忙等/拍脑袋/吞真事件；时间戳=非阻塞仲裁（W1 收口）
**状态**：✅（曾两轮暴露，已收口）

### T5 RTOS 抢占（深入一问）
**题目**：主循环有耗时任务（delay 1000）时，按键响应延迟怎么两全？
**标准/记忆点**：
- 裸机：ISR 置标志返回后主循环还在 delay 剩余时间——中断打断「执行」但不改主循环顺序
- 真正解法（FreeRTOS）：事件**进队列**（ISR=生产者）+ 按键独立任务高优先级（消费者）+ vTaskDelay **让出 CPU**（暂停自己不是暂停世界）→ 调度器级抢占，响应毫秒级
- 记忆点：**事件不进标志位、进队列；delay 从「暂停世界」变「暂停自己」**
**作答史**：
- 2026-08-06 ✅ 抢占/优先级核心答对，纠正裸机局限 + 补 RTOS 队列解法（深入一问，已回收）

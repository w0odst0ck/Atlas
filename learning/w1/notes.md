## D1 · GPIO

### Q&A

**Q1：`digitalWrite(LED_PIN, HIGH)` 芯片里发生了什么？**

<details><summary>答案</summary>

本质 = **写寄存器**：`*(GPIO_OUT_REG) |= (1 << 2)`，把输出寄存器 bit2 置 1。
芯片内部是**推挽结构**（两个 MOSFET）：HIGH = 上管导通，引脚被"推"到 3.3V 电源轨；LOW = 下管导通，拉到 0V。
硬件纳秒级响应——不是软件"告诉"灯，是开关物理接通电源。Arduino 函数只是封装。

</details>

**Q2：LED 为什么必须串 220Ω 电阻？不串会怎样？**

<details><summary>答案</summary>

LED 正向压降 ≈ 2V → 电阻分压 = 3.3 - 2 = **1.3V** → 电流 = 1.3/220 ≈ **6mA**（额定 20mA，安全）。
不串电阻：3.3V / 0Ω ≈ 无穷大 → **瞬间烧毁**；换 10Ω：130mA >> 20mA → 照样烧。
LED 是**电流器件**：决定生死/亮度的是电流，不是电压。电阻 = 限流器。

</details>

**Q3：为什么 HIGH 是 3.3V，不是 5V？**

<details><summary>答案</summary>

HIGH=3.3V 是 ESP32 的**逻辑电平**（芯片 I/O 电压，由供电/制程决定），**与电阻无关**——电阻分压是外部电路的事，别混。
3.3V = 现代低功耗主流（先进制程电压更低）；5V = Arduino Uno / TTL 时代遗产。
混接坑：3.3V 设备接 5V 信号 → 超额定值**烧芯片**；5V 设备读 3.3V → 电平不够**读不到**。解决：level shifter（W2 接 RS-485 会遇到）。

</details>

**Q4（深入一问）：LED 阳极直连 3.3V 永远亮，为什么不是可行的调光方案？**

<details><summary>答案（我的推演）</summary>

一个周期内控制高低电平的**占比**，就能控制灯的亮度——这就是 **PWM / 占空比（duty cycle）**。
原理：视觉暂留——人眼对快速切换的亮度取平均（~60Hz 以上感觉不到闪烁，LED 驱动通常 1kHz+）。
50% 占空比 = 看起来半亮。D3 呼吸灯就是改占空比，逻辑分析仪看波形。
架构回链：真实调光驱动（控制层 B1）底层就是 PWM，DALI/0-10V 只是上层协议（W3 深挖）。

</details>

### 易错点

- ⚠️ **逻辑电平 vs 电阻分压**：Q3 我答"因为电阻分压"——概念混淆。3.3V 是芯片供电/制程决定，不是外部电路分出来的
- ⚠️ **寄存器位操作直觉**：`|= (1 << n)`，bit n = 第 n 个引脚；嵌入式本质 = 读写寄存器
- ✅ pinMode 必须先于读写（不配模式直接写 = 未定义行为）

## D2 · 中断（互动课 2026-08-06）

### Q&A

**Q1：为什么轮询可能“丢事件”，而中断不会？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：轮询时 CPU 忙 → 没有窗口执行按键事件。
精确化：轮询是**采样**——只在查询瞬间“看一眼”引脚。按下→松开发生在两次查询之间 → 根本没被采样到（电平已变回）。
中断不会丢：硬件在**边沿变化瞬间触发**（边沿触发 vs 电平采样），监视是硬件做的不花 CPU，CPU 再忙也能被打断。
响应对比：轮询最坏响应 = 一个 loop 周期（可能几百 ms）；中断响应 = 微秒级。

</details>

**Q2：为什么“置标志 + 主循环消费”能同时满足 ISR 短 + 响应及时？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：置标志是原子级操作符合 ISR 短要求；主循环轮询发现标志立即执行；写读解耦保安全、响应及时。
点评精确化：
① 原子性：ESP32 上 bool/unsigned long 的 32 位对齐读写是**硬件原子**——ISR 写、主循环读不会读到撕裂值，才敢跨上下文共享。
② 及时性本质：消费的是**内存标志**（纳秒级）不是轮询硬件引脚——把“硬件事件”降维成“内存状态”，最坏响应 = 一个 loop 周期。
③ 深一层钩子（D6 揭晓）：标志只有 1 bit，连续快速按两次（间隔 < loop 周期）事件会**合并丢失** → 真实系统用计数器 / FreeRTOS 队列。

</details>

**Q3：为什么 btnPressed 必须 volatile，DEBOUNCE_MS 不需要？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：btnPressed 会被中断修改，DEBOUNCE_MS 不会。
点评精确化：
① 判据：不是“会不会被修改”，而是“是否被**当前执行流之外**修改”——ISR 是另一条执行流（硬件触发），主循环管不着它何时写 → 必须每次重新读内存。
② 常量折叠：DEBOUNCE_MS 是 const + 编译期可知 → 编译器直接把 50 内联进指令，**连内存都不读**，不存在旧值问题。
③ 即使不加 const 只在本执行流用：缓存也无风险（没人改，缓存值=真实值）。

</details>

**Q4：为什么防抖用「时间戳过滤」而不是「delay(10)」？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：delay 在 ISR 里阻塞 CPU，无法处理其他事件，时间过长导致系统重启；过短又防不住抖动；期间多次按键被忽略，整个系统都在等 delay，是糟糕的设计。时间戳是判定，满足条件才“触发”，不会强制 CPU 等时间。
点评精确化：
① 两个致命问题定性：**忙等阻塞**（CPU 停摆 + ISR 里 delay = 主循环挂起 + 看门狗复位）和**时长拍脑袋**（短了防不住 5-20ms 弹跳、长了吞掉合法快速连按；delay 期间新事件直接丢——**丢的是真事件**）。
② 时间戳方案本质：**非阻塞判定**——比较+赋值微秒级，ISR 里安全；主循环零等待。丢的是“间隔 <50ms 的噪声”，不是真事件。
③ 纠正：中断**每次下降沿都由硬件无条件触发**，时间戳不是“触发开关”——它是 ISR **内部**的仲裁：这次触发算不算有效事件。**硬件触发 vs 软件过滤，两个层面**。
④ 类比：硬件触发 = webhook 每次都推送；时间戳过滤 = 消费端去重/冷却——消息都收到，太频繁的直接丢。

</details>

### 易错点

- ⚠️ 轮询丢事件 = “没采样到”，不是“来不及处理”
- ⚠️ 防抖 = **时间过滤**，不是“等一等再读”——delay = 忙等阻塞 + 时长拍脑袋；时间戳 = 非阻塞判定
- ⚠️ 中断由硬件**无条件触发**，ISR 内过滤决定“算不算” —— 触发 ≠ 有效
- ⚠️ ISR 硬规则：禁 delay / Serial.print / malloc（阻塞 / 耗时 / 堆锁），超时触发看门狗复位

### 概念回链

- 中断/事件驱动 → 爬虫 webhook 类比；生产者-消费者 → MQ 解耦
- 防抖 → trade-pulse cooldown 同构（量化信号去重）
- 寄存器概念（D1）→ volatile 同源

### 深入一问（已回收 · 2026-08-07）

**主循环有耗时任务（delay 1000）时，按键响应延迟怎么两全？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：对事件做优先级排序，短事件优先，让按键中断打断耗时任务。
点评精确化：
① 方向对：抢占 / 优先级就是核心。中断天然能打断任何执行（硬件级）——但注意：**裸机单线程下，ISR 置标志返回后，主循环还在 delay 剩余时间里，消费仍要等**——中断能打断“执行”，但主循环的顺序没变。
② 真正解法（FreeRTOS）：事件**进队列**（ISR 只发消息 = 生产者），按键处理做成**独立任务**（消费者），优先级高于耗时任务；耗时任务一让出 CPU，按键任务立刻抢占 → 响应毫秒级。
③ 关键转变：vTaskDelay 不是忙等，是**让出 CPU**（任务进阻塞态，调度器把 CPU 给别人）——delay 从“暂停整个世界”变成“暂停自己”。
④ 记忆点：裸机 = 中断打断，但主循环忙完才理你；RTOS = 调度器抢断，高优先级任务立刻接手。事件不进标志位、**进队列**。

</details>

## D3 · PWM（互动课 2026-08-07）

### Q&A

**Q1：占空比 1% 灯什么样？频率 1kHz→20Hz 又会怎样？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：1% 占空比灯看起来和灭了一样；频率降低周期变长，灯看起来忽明忽灭。
点评精确化：
① 1% ≈ 灭但没灭：亮度 = 平均光能 = 满亮的 1%（人眼对暗部敏感度非线性，1% 可能比“1% 亮度”略可感，但接近灭）；**占空比 0% 才是真灭**。
② 20Hz < 视觉暂留下限（~60Hz）→ 人眼能分辨亮暗交替 → **频闪**。真实照明里低频 PWM 会造成头晕、相机拍摄出现频闪带——你做的智能照明 / EMC 场景，LED 驱动器频闪是行业指标（IEEE 1789）。
③ 核心拆解：**占空比 → 亮度（平均光能），频率 → 是否可见闪烁（视觉暂留下限）**——两个独立维度。
④ 记忆点：占空比 = 亮度旋钮，频率 = 闪烁消除器（≥1kHz 人眼不可见）。

</details>

**Q2：为什么行业不用“直接调小电流”的模拟调光来规避 PWM 的 EMI 问题？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：直接调电流影响灯具参数，比如色温、效率，而且能量损耗大。
点评精确化：
① 色温偏移机制：LED 电流变化 → 发光波长漂移（蓝光芯片 + 荧光粉方案）→ 调暗时颜色跟着变；PWM 恒流下电流始终不变 → 色温 / 光效恒定，这是照明质量的根本保证。
② 损耗量化：线性调流 = 多余能量全变热（(V_in − V_LED) × I），调暗时压差占比更大、效率更差；PWM 恒流开关 = 开关电源效率 90%+。
③ 行业结论：PWM 的缺点（EMI）是**工程问题**——频率抖动 / 软开关 / 滤波器能修；调流的缺点（色温 / 效率）是**原理问题**——没得修。所以行业宁可做 EMC 处理也不回模拟调流。
④ 记忆点：EMI 能修，色温不能修——选“原理级优点 + 工程级缺点”的那条路。

</details>

**Q4：分辨率 8bit vs 16bit，为什么低亮度档位跳变可见、高亮度看不出？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：人眼对光的感知靠相对亮度变化；编码比特是均匀划分档位，低亮度相对变化大，所以跳变可见。不均匀划分档位（反比例/对数映射）可改善。
点评精确化：
① 本质 = 韦伯-费希纳定律：感知亮度 ∝ log(光强)，人眼是**对数感知**（进化来的动态范围扩展——自然光强跨 10 个数量级，线性感知扛不住，所以暗处放大、亮处压缩）。
② 矛盾链条：编码均匀分档（光强等差）× 人眼对数感知（感知差递减）= 低端每档翻倍级跳变、高端 0.5% 级无感。
③ 数据佐证：低亮度 1→2 相对变化 +100% 可见；高亮度 200→201 只 +0.5% 无感。
④ 行业解法（用户答对）：不均匀划分 = **gamma 校正 / 非线性调光曲线**，三种落地：软件 LUT（8bit 硬件+查表，成本零最常见）/ DALI 协议自带对数曲线 / 硬件 16bit 硬救低端。
⑤ 记忆点：目标不是光强均匀，是**感知均匀**——感知均匀才是调光质量。

</details>

**知识点 5：ledcWrite vs digitalWrite（2026-08-08 已讲，检验题待答）**

<details><summary>Q5 知识点5 检验（2026-08-11 已答 ✅）</summary>

- digitalWrite = CPU 手动翻转引脚寄存器，产生 PWM 要 CPU 每周期参与，频率越高 CPU 绑得越死
- ledcWrite = ESP32 LEDC 硬件定时器外设：CPU 写一次占空比数值，外设自动生成方波，CPU 完全退出
- 对比：digitalWrite 高占用/波形随代码负载抖动；ledcWrite 近零占用/硬件时序稳定
- 主线呼应：D2 中断解放 CPU 等按键，D3 外设解放 CPU 翻波形——**CPU 稀缺，能交给外设的绝不自己干**
- 16 通道、频率/分辨率独立可配 = W3 调光驱动底层肌肉（0-10V/DALI 骑在 PWM 上的协议）
- **原答**：① digitalWrite 是 CPU 控制翻转，ledcWrite 不需要 CPU 参与由定时器设置 ② CPU 被拖累每次都要参与，且 CPU 有被打断可能，波形不稳定
- **批改**：① 肯定：抓住了"谁在干活"（CPU vs 外设），这是本质 ② 精确化：digitalWrite = CPU 每周期执行写寄存器指令；ledcWrite = CPU 写一次比较值（CCR），之后外设后台自动翻转 ③ 纠正：小修正——ledcWrite 不是"完全不需要 CPU"，CPU 要参与一次（下单），只是不参与每周期翻转 ④ 记忆点：**CPU 只下单，外设干活**
- **正解**：1kHz 呼吸灯用 digitalWrite → CPU 被周期性实时要求绑死（每 500μs 精确翻转一次，期间不能被打断太久）；中断会推迟翻转时机 → 占空比/频率抖动（呼吸灯变"咳嗽灯"）

</details>

### 易错点

- ⚠️ 占空比管亮度（平均光能），频率管闪烁（视觉暂留下限 ~60Hz）——别混
- ⚠️ 1% ≈ 灭但不是灭，0% 才是真灭
- ⚠️ 调光三选：PWM = 色温稳 / 效率高 / EMI 可修（工程问题）；调流 = 色温漂 / 损耗大（原理问题）
- ⚠️ 8bit 低亮度跳变可见 = 编码均匀 × 人眼对数感知；调光目标是感知均匀（gamma/对数曲线）
- ⚠️ ledcWrite 不是"CPU 完全不管"——CPU 要参与一次（写占空比），只是不参与每周期翻转；本质 = 把周期性精确动作外包给硬件

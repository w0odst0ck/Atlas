## D1 · GPIO

### Q&A

**Q1：`digitalWrite(LED_PIN, HIGH)` 芯片里发生了什么？**

<details><summary>答案</summary>

本质 = **写寄存器**：`*(GPIO_OUT_REG) |= (1 << 2)`，把输出寄存器 bit2 置 1。
芯片内部是**推挽结构**（两个 MOSFET）：HIGH = 上管导通，引脚被"推"到 3.3V 电源轨；LOW = 下管导通，拉到 0V。
硬件纳秒级响应——不是软件"告诉"灯，是开关物理接通电源。Arduino 函数只是封装。

</details>

**Q2：LED 为什么必须串 220Ω 电阻？不串会怎样？**

<details><summary>答案</summary>

LED 正向压降 ≈ 2V → 电阻分压 = 3.3 - 2 = **1.3V** → 电流 = 1.3/220 ≈ **6mA**（额定 20mA，安全）。
不串电阻：3.3V / 0Ω ≈ 无穷大 → **瞬间烧毁**；换 10Ω：130mA >> 20mA → 照样烧。
LED 是**电流器件**：决定生死/亮度的是电流，不是电压。电阻 = 限流器。

</details>

**Q3：为什么 HIGH 是 3.3V，不是 5V？**

<details><summary>答案</summary>

HIGH=3.3V 是 ESP32 的**逻辑电平**（芯片 I/O 电压，由供电/制程决定），**与电阻无关**——电阻分压是外部电路的事，别混。
3.3V = 现代低功耗主流（先进制程电压更低）；5V = Arduino Uno / TTL 时代遗产。
混接坑：3.3V 设备接 5V 信号 → 超额定值**烧芯片**；5V 设备读 3.3V → 电平不够**读不到**。解决：level shifter（W2 接 RS-485 会遇到）。

</details>

**Q4（深入一问）：LED 阳极直连 3.3V 永远亮，为什么不是可行的调光方案？**

<details><summary>答案（我的推演）</summary>

一个周期内控制高低电平的**占比**，就能控制灯的亮度——这就是 **PWM / 占空比（duty cycle）**。
原理：视觉暂留——人眼对快速切换的亮度取平均（~60Hz 以上感觉不到闪烁，LED 驱动通常 1kHz+）。
50% 占空比 = 看起来半亮。D3 呼吸灯就是改占空比，逻辑分析仪看波形。
架构回链：真实调光驱动（控制层 B1）底层就是 PWM，DALI/0-10V 只是上层协议（W3 深挖）。

</details>

### 易错点

- ⚠️ **逻辑电平 vs 电阻分压**：Q3 我答"因为电阻分压"——概念混淆。3.3V 是芯片供电/制程决定，不是外部电路分出来的
- ⚠️ **寄存器位操作直觉**：`|= (1 << n)`，bit n = 第 n 个引脚；嵌入式本质 = 读写寄存器
- ✅ pinMode 必须先于读写（不配模式直接写 = 未定义行为）

## D2 · 中断（互动课 2026-08-06）

### Q&A

**Q1：为什么轮询可能“丢事件”，而中断不会？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：轮询时 CPU 忙 → 没有窗口执行按键事件。
精确化：轮询是**采样**——只在查询瞬间“看一眼”引脚。按下→松开发生在两次查询之间 → 根本没被采样到（电平已变回）。
中断不会丢：硬件在**边沿变化瞬间触发**（边沿触发 vs 电平采样），监视是硬件做的不花 CPU，CPU 再忙也能被打断。
响应对比：轮询最坏响应 = 一个 loop 周期（可能几百 ms）；中断响应 = 微秒级。

</details>

**Q2：为什么“置标志 + 主循环消费”能同时满足 ISR 短 + 响应及时？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：置标志是原子级操作符合 ISR 短要求；主循环轮询发现标志立即执行；写读解耦保安全、响应及时。
点评精确化：
① 原子性：ESP32 上 bool/unsigned long 的 32 位对齐读写是**硬件原子**——ISR 写、主循环读不会读到撕裂值，才敢跨上下文共享。
② 及时性本质：消费的是**内存标志**（纳秒级）不是轮询硬件引脚——把“硬件事件”降维成“内存状态”，最坏响应 = 一个 loop 周期。
③ 深一层钩子（D6 揭晓）：标志只有 1 bit，连续快速按两次（间隔 < loop 周期）事件会**合并丢失** → 真实系统用计数器 / FreeRTOS 队列。

</details>

**Q3：为什么 btnPressed 必须 volatile，DEBOUNCE_MS 不需要？**

<details><summary>答案（我的表述 + 点评）</summary>

我的表述：btnPressed 会被中断修改，DEBOUNCE_MS 不会。
点评精确化：
① 判据：不是“会不会被修改”，而是“是否被**当前执行流之外**修改”——ISR 是另一条执行流（硬件触发），主循环管不着它何时写 → 必须每次重新读内存。
② 常量折叠：DEBOUNCE_MS 是 const + 编译期可知 → 编译器直接把 50 内联进指令，**连内存都不读**，不存在旧值问题。
③ 即使不加 const 只在本执行流用：缓存也无风险（没人改，缓存值=真实值）。

</details>

## 1. 背景与目标

### 1.1 背景
- 公司主营物联网灯具节能改造（格兰斯贝方案：GS-LINKER 无线 Mesh + 24G/5.8G 雷达存在感应 + 恒照度光感 + 云平台能耗，节能率 70-80%）
- 个人方向：软考网络工程师（2026 下半年，10 月底）→ HCIA-Datacom → 边缘计算 AI
- 目标：仿真 demo 讲清产品故事 + 网络考点真实可见 + 为边缘 AI 硬件阶段铺路

### 1.2 目标
1. 复现格兰斯贝核心逻辑：Mesh 节点、存在感应、恒照度调节、分组联动、能耗看板
2. 软考网络考点实践化：TCP/IP、802.11/CSMA-CA、路由协议、VLAN、DHCP/DNS、IPv6 仿真可见、可抓包
3. 边缘 AI 入口：策略引擎纯逻辑（无 I/O 依赖），Phase 2 移植 ESP32；传感器→推理→控制链路设计

### 1.3 非目标（本期不做）
- 不做真实调光色温算法（简化功耗模型）、不做碳交易/分时电价（预留 tariff 钩子）、不做多用户权限/生产级云平台

## 2. 总体架构

```
┌────────────────────────────────────────────────┐
│  Web Dashboard（单页，零构建）                   │
│  · 场景 2D 视图（车库/办公室，灯亮灭实时渲染）   │
│  · 能耗看板：改造前 vs 改造后 曲线 + 节能率       │
│  · Mesh 拓扑图：节点状态 / 链路 / 自愈 / 冲突统计 │
└───────────────────┬────────────────────────────┘
                    │ WebSocket（实时状态）+ REST（控制）
┌───────────────────▼────────────────────────────┐
│  仿真核心（Python 3.13 / asyncio + 虚拟时钟）     │
│  · scene.py      场景定义：灯具节点/传感器/移动体 │
│  · engine.py     事件引擎 + 虚拟时钟（可配 60x/600x）│
│  · strategy.py   策略引擎（含仲裁表，见 §3.2）    │
│  · energy.py     能耗模型 + 审计日志（每 kWh 可归因）│
│  · mesh.py       Mesh 模拟：CSMA/CA 信道 + 路由双模式 │
│  · transport.py  传输层抽象（Local/MQTT/WS 可插拔）│
│  · broker.py     极简 MQTT broker（教学用）        │
└───────────────────┬────────────────────────────┘
                    │ MQTT（上行 telemetry / 下行 command）
┌───────────────────▼────────────────────────────┐
│  网络学习层                                      │
│  · 内嵌 broker（Phase 1）→ mosquitto（M4 抓包）   │
│  · GNS3（Phase 3 主线：VLAN/STP/路由/ACL/NAT）    │
└────────────────────────────────────────────────┘
```

**关键决策**：
- **虚拟时钟是 M1 前置**：所有节点定时器/延时走虚拟时钟调度（`engine.clock`），禁止混入 `asyncio.sleep` 真实时间——保证可复现、可加速（1s=1min 或 600x）
- 业务逻辑与传输解耦：事件总线 → 可插拔传输层
- **Mesh 仿真 ≠ 可抓包**：mesh.py 是进程内模型（可视化+日志演示）；可抓真包范围 = 仿真核心↔broker 的 MQTT over TCP（Wireshark）

## 3. 场景与节能策略

### 3.1 场景模型
- 默认场景：地下车库（4 车道 × 5 灯 = 20 节点），可切换办公室（16 节点）；场景数据复用 Atlas scene-library（`underground_garage.toml` 等）
- 每节点：额定功率（车库 36W / 办公 18W）、亮度 0-100%、雷达状态、光感读数、分组、路由表
- **移动体**：有位置 + 朝向 + 速度状态机，触发雷达按**覆盖范围**判定（圆形区域），非"路径经过"点判定

### 3.2 策略引擎（含仲裁表，P0 修订）

**仲裁规则（存在感应优先，有人时恒照度调节）**：

| 优先级 | 策略 | 触发 | 输出 | 抑制规则 |
|---|---|---|---|---|
| 1 | 存在感应 | 雷达检测到人/车 | 亮度 → 100% | 无 |
| 2 | 恒照度 | 人在场 + 照度 < 目标 | 按反馈补偿调亮 | 被存在感应覆盖（已在 100%） |
| 3 | 休眠 | 人离开 + 延时 T=60s | 亮度 → 15% | 恒照度不介入休眠态 |
| 4 | 车道联动 | 车辆接近 | 前方 N=4 盏依次点亮 | 受仲裁表约束 |

**恒照度模型（反馈闭环，P0 修订）**：
- 光感读数 = 环境光 + k × 灯具亮度贡献（k=灯具对传感器视场贡献系数）
- 控制器：误差 = 目标照度(300lx) − 实测照度 → 死区 ±20lx 内不动作 → 输出亮度增量（比例控制，限幅）
- **不是查表前馈**：v1.0 的"读环境光→查表补偿"是开环，已废弃；反馈 + 死区防抖才是真实恒照度

### 3.3 能耗模型（验收重构，P0 修订）
- 实际功耗：`P(L) = P_rated × (0.1 + 0.9 × L)`
- 改造前基线：24h 全亮；改造后：策略引擎驱动
- **审计日志**：每灯每小时能耗可归因到策略决策（哪个策略状态、占空比、时长）→ energy.py 输出审计表
- **验收标准（v1.1 重构）**：
  1. 策略行为正确性（人走延时、联动顺序、恒照度收敛、仲裁表生效）——逻辑对错，单测覆盖
  2. 能耗可解释性（审计表能拆到每度电归因）——可信度
  3. 节能率 = **输出**（按场景工况声明：车库/办公室分别报告），不是验收目标；对齐格兰斯贝 60-80% 作为"工况合理时的参考区间"

## 4. Mesh 网络模拟（软考考点载体，P1 修订）

- **链路模型**：节点间距 → RSSI 衰减 → 通信成功率（自由空间模型）
- **信道模型（新增，U1）**：CSMA/CA 真建模——载波侦听、随机退避（指数退避）、ACK 确认、冲突检测 → **冲突率/重传率统计**（上午题考点可视化）
- **路由双模式（新增，U2）**：AODV（距离矢量）vs 链路状态（OSPF 风格洪泛/LSA）——收敛时间对比，考点直接可见
- **自愈演示**：拔中继 → 邻居失效 → 重路由 → 拓扑动画
- **故障注入**：丢包率、节点离线，观察降级
- **测试**：mesh 单测（路由收敛/断链重路由/丢包降级）——P1 补充，不靠肉眼

> 抓包边界（P1 澄清）：Mesh 层 = 日志+可视化演示；可抓真包 = MQTT over TCP（M4 mosquitto）
